Slide a small window: convolution

Session 1 ended with a problem: flattened into a row of 784, an image forgets which pixel sat next to which. Convolution puts the neighbours back. A small window of nine weights sits over a 3 x 3 patch, multiplies, sums, writes one number, and slides one step. Do that at every position and you have a new grid that answers one question everywhere at once: is there a vertical edge here? Tonight we compute that by hand on a real pair of trousers, watch four kernels disagree about the same pixels, and build the exact 288-number feature layer the label budget bench runs on.

Part 1 · covers kernels as weighted sums

Nine weights, multiplied and summed

5 min live

Take Fashion-MNIST test image 2, a pair of trousers, and put a 3 x 3 window over rows 16 to 18, columns 10 to 12: the inner edge of the left leg, where cloth gives way to the gap between the legs. The vertical-edge kernel has nine weights. Multiply each pixel by the weight on top of it, add the nine products, divide by 4, take the absolute value. That is one output cell. Everything else in convolution is doing this again, one step to the right.

LiveCross-correlation, and why libraries call it convolution3 min▶

In the mathematical definition of convolution, the kernel is flipped top-to-bottom and left-to-right before it slides. What you just did, and what every deep learning library does, skips the flip. That operation has its own name, cross-correlation. Goodfellow, Bengio and Courville say it plainly in Deep Learning, section 9.1: "Many machine learning libraries implement cross-correlation but call it convolution".

Why nobody minds: when the kernel's weights are learned, the network simply learns the flipped version, and the results are identical. It matters only when you copy a hand-made kernel from a textbook into code. A vertical-edge kernel flipped left-to-right is the same kernel with its sign reversed, so a positive response becomes a negative one. That is one reason the widget and the build-along take the absolute value: they report edge strength, not edge direction.

Check yourself before the widget: the patch above gives -347 before dividing. Which side of the patch is brighter? The left (237, 239, 245 against 113, 151, 198), so the kernel, which weighs right minus left, comes out negative.

Self-studySparse interactions and parameter sharing4 min▶

Section 9.2 of Goodfellow et al. says convolution "leverages three important ideas": sparse interactions, parameter sharing and equivariant representations. All three are visible in one picture.

Sparse interactions. Each output cell looks at 9 of the 784 input pixels, never the rest. The cell at row 16, column 10 has no idea what the trouser waistband looks like.

Parameter sharing. The same nine weights are reused at all 676 positions of the 26 x 26 output. The kernel that finds the inner edge of the left leg finds the outer edge of the right leg with no extra weights. That is why the widget's readout says "9, reused at every position".

Equivariance. Shift the trousers two pixels right and the edge map shifts two pixels right with it: the responses move, they do not change. Part 3 shows what pooling adds on top of that, and what it does not.

How much this saves against a layer that connects every pixel to every output is a parameter count, and Part 3 points to where that count lives. Here the point is smaller and more practical: one kernel, nine numbers, the same question asked everywhere.

Real world

Nine weights over a full camera frame (constructed Corvane example). Corvane's camera, as constructed in session 1, takes 1280 x 720 frames. A 3 x 3 kernel with no padding fits at 1278 x 718 = 917,604 positions per channel, and it uses the same nine weights at every one of them. The cost of a kernel grows with the image; the number of things it can learn does not. That is why a kernel tuned on 28 x 28 garments can be run on a full frame at all, and also why it will happily fire on anything in the frame with the same local pattern, including things that are not items.

Part 2 · covers edges, blur and sharpen on real pixels

What each kernel responds to

6 min live

Change the nine weights and you ask the pixels a different question. A vertical-edge kernel asks "does brightness change left to right here?", a horizontal one asks "top to bottom?", a box blur asks "what is the local average?", and a sharpen kernel asks "how much does this pixel stand out from its four neighbours?". Run all four on the same real images and the answers disagree in ways that tell you what the garment is shaped like.

LiveTry it: four clicks, four answers4 min▶

The widget below holds the same 20 real Fashion-MNIST test images as session 1, at full 28 x 28 size. It opens on the Trouser with the vertical-edge kernel. Read the readout: output 26 x 26, strongest response 255.0, 228 positions above 40.

Now click, in this order:

1. horizontal edge (Trouser still selected): the count drops to 44. Trousers are two long vertical tubes; there is very little top-to-bottom change except the waistband and the hems.

2. the Sneaker thumbnail, horizontal edge still on: 182. Then back to vertical edge: 72. The sole is one long horizontal edge, and the kernels say so without anyone telling them what a shoe is.

3. the T-shirt, then sharpen: strongest response 824.0. The input lives between 0 and 255; the output does not. A centre weight of 5 against four weights of -1 can amplify a bright pixel on a dark rim far beyond the ceiling. The picture caps at 255 for display, the number does not.

4. 2x2 max pool: on. The output shrinks to 13 x 13. Keep that button in mind for Part 3.

Self-studyWhy the divisor, and why a response can leave the range3 min▶

Each kernel's weights decide the range of its output. The box blur's nine weights sum to 9, so dividing by 9 makes it an average: it can never leave 0 to 255, and on the Trouser it peaks at 247.2. The edge kernels' positive weights sum to 4 and their negative weights to -4, so dividing by 4 maps a perfect black-to-white step to exactly 255, which is the Trouser's strongest vertical response.

The sharpen kernel's weights sum to 1, so a flat patch comes out unchanged, but it is not an average. Its range runs from -1,020 to 1,275 on 8-bit input. On the T-shirt it reaches 824.0, on the Sandal 854.0. Any pipeline that writes that back into uint8 without thinking either clips it (detail lost) or wraps it (session 1's bug, in a new place). Decide the scaling before the kernel, and write it down next to the kernel.

Real world

The belt seam that looks like an item (constructed Corvane example). Corvane's conveyor belt is made of joined sections. Wherever two sections meet there is a seam running straight across the belt, and under the camera it is a strong horizontal edge in every frame where it passes, item or no item. A horizontal-edge feature cannot tell a seam from the sole of a shoe or the hem of a jacket: both are "brightness changes top to bottom". On Fashion-MNIST this never shows up, because the background is an exact 0 everywhere. On the line it is the first thing an edge feature finds. Write the belt into the image card's "is not" field, and test a frame with no item on it before trusting any edge count.

Part 3 · covers stride, padding, pooling, learned kernels

Stride, padding, pooling, and kernels that learn

4 min live

Three settings decide the shape of what comes out: whether the image gets a border of zeros (padding), how far the window jumps each step (stride), and whether neighbouring outputs are then merged (pooling). Shape bugs in vision code are nearly always one of these three, and all three are one line of arithmetic.

LivePooling buys tolerance to small shifts, not to everything3 min▶

Max pooling replaces each 2 x 2 block with its largest value. In the figure, the block from the trouser edge map holds 86.75, 242.5, 45.5 and 238.5, and only 242.5 survives. If the trousers moved one pixel, the strong edge would still be somewhere in that block most of the time, and the pooled value would barely change. Goodfellow et al., section 9.3, put it this way: pooling makes the representation "approximately invariant to small translations of the input".

Read the words carefully: approximately, small, translations. Pooling does nothing for a flip. Mirror a sneaker and its toe moves from one side of the image to the other, far beyond what any 2 x 2 block can absorb. The vertical-edge map is mirrored too, and every pooled number lands in a different place. Session 5 measures exactly that on the bench's model and watches shoes fail.

Turn the widget's pool button on and off on the Trouser: the picture halves, the strong edges stay visible, and their exact positions blur into blocks. That is the trade, written in pixels.

Self-studyWhy a learned kernel beats a hand-made one4 min▶

Every kernel on this page was chosen by a person. The bench's feature layer uses eight of them: Sobel-style edges in four directions (vertical, horizontal and two diagonals), each split into a positive and a negative half. They are a sensible guess at what matters, and the bench shows the guess is decent: in session 4 they reach 75.8% at 300 labels against 74.8% for raw pixels.

A convolutional network does not guess. It starts with random weights and adjusts them by gradient descent until the kernels are whatever helps the task. Yosinski, Clune, Bengio and Lipson (2014) looked at what those first-layer kernels become and report, in their abstract, that they resemble Gabor filters and colour blobs, and that they are general: similar across datasets and tasks. Gabor filters are oriented edge and stripe detectors at several scales, which is the hand-made Sobel idea done more finely and in more directions, and learned colour blobs are something greyscale Sobel kernels cannot express at all. The bench's eight kernels are exactly what learning would replace.

Training those kernels needs backpropagation through the convolution and a training loop; both have their own sessions, and the architectures that stack learned kernels, with their parameter counts, are in Deep Learning session 4 ↗. The professional habit worth keeping from here: when a hand-made feature underperforms, the first question is not "which kernel next?" but "should the kernels be learned, and do I have the labels to learn them?". Session 4 puts a number on the second half.

Further reading on linear filtering in general: Szeliski, Computer Vision: Algorithms and Applications, 2nd ed. (2022), reported.

Real world

Why pretrained networks travel. The Yosinski et al. result is the reason transfer learning works in practice. If the first layers of a network trained on a large, general dataset have already learned general edge and blob detectors, a team with a few hundred labelled images of its own does not need to learn those layers again: it can reuse them and spend its scarce labels on the last, specific layers. The same paper reports that features become more specific to the original task by the last layer, so how much to reuse is itself a decision. Session 6 brings this to Corvane's scope note (constructed Corvane example).

Write convolution with slicing, and check it against the widget. Instead of looping over 676 positions, loop over the nine weights: each weight multiplies one shifted 26 x 26 slice of the image, and the nine slices add up. Same arithmetic as Part 1, nine array operations instead of 6,084 scalar ones. Widen to float first: session 1's uint8 trap is waiting. Then print the cell from the figure and the one next to it.

★ Step 2 · conv2d_valid on the TrouserVERT = np.array([[-1, 0, 1], [-2, 0, 2], [-1, 0, 1]], dtype=np.float64) HORZ = VERT.T # [[-1,-2,-1],[0,0,0],[1,2,1]] def conv2d_valid(img, k): """Cross-correlation, stride 1, no padding: what libraries call convolution.""" img = img.astype(np.float64) oh, ow = img.shape[0] - k.shape[0] + 1, img.shape[1] - k.shape[1] + 1 out = np.zeros((oh, ow)) for a in range(k.shape[0]): for b in range(k.shape[1]): out += k[a, b] * img[a:a + oh, b:b + ow] return out trouser = x_test[2] v = np.abs(conv2d_valid(trouser, VERT) / 4) h = np.abs(conv2d_valid(trouser, HORZ) / 4) print(v.shape) # (26, 26) print((v > 40).sum(), (h > 40).sum()) # 228 44 print(v[16, 10], v[16, 11]) # 86.75 242.5

★ Step 4 · max_pool2def max_pool2(m): h, w = m.shape[0] // 2 * 2, m.shape[1] // 2 * 2 return m[:h, :w].reshape(h // 2, 2, w // 2, 2).max(axis=(1, 3)) p = max_pool2(v) print(v.shape, "->", p.shape) # (26, 26) -> (13, 13) print((p > 40).sum(), "of", p.size) # 76 of 169

Build the bench's feature layer. Shrink the image to 14 x 14 by averaging each 2 x 2 block, run four Sobel-direction kernels, split each response into its positive half (ReLU of +r, dark-to-light edges) and negative half (ReLU of -r, light-to-dark edges), and max pool. Eight maps of 6 x 6 is 288 numbers. The first 72 come from the vertical kernel and the next 72 from the horizontal one, so summing them is a quick check that the features remember what the widget showed. These sums are build-along numbers; your run on the full files should print the same, and they are not bench canon.

★ Step 5 · 288 featuresKERNELS = { "vertical": VERT, "horizontal": HORZ, "diag_down": np.array([[0, 1, 2], [-1, 0, 1], [-2, -1, 0]], dtype=np.float64), "diag_up": np.array([[2, 1, 0], [1, 0, -1], [0, -1, -2]], dtype=np.float64), } def shrink(img): # mean of each 2 x 2 block: 28 -> 14 return img.astype(np.float64).reshape(14, 2, 14, 2).mean(axis=(1, 3)) def features(img): small = shrink(img) # 14 x 14 parts = [] for k in KERNELS.values(): r = conv2d_valid(small, k) / 4 # 12 x 12 parts.append(max_pool2(np.maximum(r, 0)).ravel()) # +r, ReLU, pool: 36 parts.append(max_pool2(np.maximum(-r, 0)).ravel()) # -r, ReLU, pool: 36 return np.concatenate(parts) # 8 x 36 ft, fs = features(trouser), features(sneaker) print(shrink(trouser).shape, ft.shape) # (14, 14) (288,) print(ft[:72].sum().round(), ft[72:144].sum().round()) # 5170.0 1005.0 trouser: vertical wins print(fs[:72].sum().round(), fs[72:144].sum().round()) # 1098.0 2555.0 sneaker: horizontal wins

Check yourself

Three questions

Clear all three and session 2 gets stamped in your passport.

1 · A 3 x 3 kernel slides over a 28 x 28 image with stride 1 and no padding. Why is the output 26 x 26?

Valid convolution only computes where the whole window fits. A 5 x 5 kernel would give 24; padding with one ring of zeros brings a 3 x 3 back to 28. The general rule is floor((input + 2 x padding - kernel) / stride) + 1.

2 · On the Trouser, the vertical-edge kernel gives 228 positions above 40 and the horizontal kernel gives 44. What does that tell you?

Neither kernel is "more sensitive": the same pair reverses on the Sneaker. The counts describe the garment's shape, which is why edge features already separate some classes before any model is trained.

3 · A 2 x 2 max pool helps when an item shifts by one pixel. Why does it not help when the item is flipped left to right?

A flip keeps every pixel value and moves it, which is the opposite of what option C says. Goodfellow et al. 9.3 says pooling is "approximately invariant to small translations": small, and translations. Session 5 measures what a flip does to the bench's shoes.
